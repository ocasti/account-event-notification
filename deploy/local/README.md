# deploy/local/

Everything the local stack needs besides the application code. `compose.yaml` in this
directory wires it together; the `Makefile` at the repository root wraps the usual commands
(`docker compose -f deploy/local/compose.yaml --env-file .env ...`). The Dockerfiles live in
`docker/` at the repository root and are built with the repository root as context.

| Path | What it is |
|---|---|
| `compose.yaml` | Local stack: profiles `infra`, `app`, `observability`. Build contexts point at `../..` with `docker/notifications.Dockerfile` and `docker/simulator.Dockerfile`; every other path is relative to this directory; variables are interpolated from the root `.env` through `--env-file .env`. |
| `../../docker/notifications.Dockerfile` | Multi-stage build of `services/notifications` (the `infrastructure` module). One image for `notifications-api` and `notifications-worker`; the role comes from `SPRING_PROFILES_ACTIVE`. |
| `../../docker/simulator.Dockerfile` | Multi-stage build of `services/event-simulator`. Bundles `docs/notification_events.json` as the reference data set. |
| `elasticmq/custom.conf` | Queues declared on start: `account-events` (visibility 30 s, long polling 20 s) and its DLQ `account-events-dlq` (`maxReceiveCount = 5`). The image is pinned to `elasticmq-native:1.6.12`: 1.7.x removed the statistics/UI server on 9325. |
| `wiremock/mappings/` | Webhook test double. `POST /webhook` returns 200, except when the body contains `"EVT003"`, `"EVT005"` or `"EVT009"` (503). `POST /webhook-slow` returns 200 after 10 s to exercise the read timeout. |
| `prometheus/prometheus.yml` | Scrapes `/actuator/prometheus` every 5 s from `notifications-api` and from every `notifications-worker` replica (DNS service discovery), plus `postgres-exporter:9187` (job `postgres`) and `node-exporter:9100` (job `node`, see "node_exporter" below). Loads `prometheus/alerts.yml` via `rule_files`. |
| `prometheus/alerts.yml` | The alarms from RFC section 16 plus the ones added for this service review and for Postgres/container load, as Prometheus rules (see "Alarms" below). |
| `postgres-exporter/queries.yaml` | Business queries for `prometheuscommunity/postgres-exporter` (gauges `cobre_*`: events by status, overdue/claimed/executed attempts, age of the oldest one). Mounted into the exporter via `PG_EXPORTER_EXTEND_QUERY_PATH`. |
| `grafana/provisioning/` | Prometheus datasource (default) and two dashboards: `Notifications` (delivery rate by status, webhook p95 by client, attempts due, failures by client) and `Notifications · Service review` (`notifications-service.json`, see "What to look at in Grafana" below). Anonymous access as Admin. |
| `keys/` | RS256 key pair generated by `make keys`; `.pem` files are git-ignored. Mounted read-only at `/keys` in api and worker. |

## Profiles

| Profile | Services |
|---|---|
| `infra` | `postgres`, `elasticmq`, `wiremock` |
| `app` | `notifications-api`, `notifications-worker`, `event-simulator` |
| `observability` | `prometheus`, `grafana`, `postgres-exporter`, `node-exporter` |

Start order is enforced with `depends_on` + `condition: service_healthy`:
postgres and elasticmq -> notifications-api (runs Flyway) -> notifications-worker -> event-simulator.

## Running

All commands run from the repository root:

```bash
cp .env.example .env            # once; only WEBHOOK_URL needs changing for a real receiver
make keys                       # RS256 key pair in deploy/local/keys/
make infra                      # postgres + elasticmq + wiremock
make up                         # infra + api + worker + simulator (builds the images)
make up-all                     # everything, including prometheus + grafana
docker compose -f deploy/local/compose.yaml --env-file .env --profile infra --profile app up -d --scale notifications-worker=4   # competing consumers
make down
```

Host ports come from `.env`: API `8080`, simulator `8090`, WireMock `8089`, ElasticMQ UI `9325`,
Prometheus `9090`, Grafana `3001`, Postgres `5432`.

Quick checks:

```bash
curl -s -X POST localhost:8089/webhook -d '{"id":"EVT003"}' -o /dev/null -w '%{http_code}\n'   # 503
curl -s localhost:9325/statistics/queues                                                      # both queues
open http://localhost:3001                                                                   # dashboard
```

Memory limits per container add up to about 2.7 GB with one worker replica; each extra
worker adds 512 MB.

## What to look at in Grafana

`open http://localhost:3001` (anonymous, Admin) opens the `Notifications` dashboard, with four panels:

| Panel | PromQL query | What it means |
|---|---|---|
| **Delivery rate by status** | `sum by (status) (rate(notifications_deliveries_total[1m]))` | Deliveries per second, split by the final status of the attempt (`completed`/`retrying`/`failed`). A sustained rise in `failed` is the first sign of a client's webhook being down. |
| **Webhook latency p95 by client** | `histogram_quantile(0.95, sum by (le, client_id) (rate(notifications_webhook_latency_seconds_bucket[1m])))` | p95 of the webhook POST, by client. Detects degradation of a specific client's endpoint before it starts failing. |
| **Attempts due** | `max(notifications_attempts_due)` | Overdue attempts not yet claimed by any worker (gauge published by each replica, aggregated with `max`, never summed). If it rises, the workers cannot keep up: scale replicas or check Postgres. |
| **Failures by client (selected range)** | `sum by (client_id) (increase(notifications_deliveries_total{status="failed"}[$__range]))` | Table with the failure count by client over the last hour. Answers directly "which client is having problems?" without touching the attempts table. |

**What the code publishes today.** `notifications_attempts_due` is published by each worker replica
(`DueAttemptsGaugeUpdater`). `notifications_deliveries_total` and `notifications_webhook_latency_seconds`
are emitted by the port decorators `MeteredNotificationEventRepository` and `MeteredWebhookSender`
(`services/notifications/infrastructure/.../worker/`), which wrap the repository and the webhook
sender in the worker process; `WorkerProfileBootIT` checks that they are the effective beans. With
`make up-all` all four panels show data as soon as the simulator emits events.
`notifications_duplicates_total` counts queue redeliveries with an `event_id` already registered (ingestion
idempotency); the worker discards them and leaves a DEBUG line `duplicate account event ignored` with `event_id` and `client_id`.
`notifications_leases_expired_total` is still not emitted: the claim with `SKIP LOCKED` does not distinguish an
expired lease from a new attempt, so that counter remains future work.

### Logs

Every delivery attempt leaves a `webhook delivery attempt` line in the worker with key-value pairs:
`event_id`, `client_id`, `cycle`, `attempt_number`, `outcome` (`success`, `transient_failure`,
`permanent_failure`), `response_status`, `latency_ms`, and `reason` on failures. It never includes the body
or the signature. For JSON output (ECS format), add the `json` profile:
`SPRING_PROFILES_ACTIVE=worker,local,json`. Correlate with Grafana by filtering on `client_id`, or with the
API by `event_id`.

## Service review dashboard: `Notifications · Service review`

`open http://localhost:3001` (anonymous, Admin) -> `Notifications · Service review` dashboard
(uid `notifications-service`, `deploy/local/grafana/provisioning/dashboards/notifications-service.json`).
Leaves the original `Notifications` dashboard untouched. Variables: `client_id` (multi, includes
"All", from `notifications_deliveries_total`) and `instance` (multi, includes "All", `notifications-worker`
replica, from `notifications_attempts_due`). Nine rows, **all expanded**
(`collapsed: false`, no nested panels): opening the dashboard shows everything at once, with no need
to expand each row by hand. The order is `Summary` -> `Postgres load` -> `Deliveries` ->
`Ingestion` -> `Errors` -> `HTTP API` -> `JVM and process` -> `Database` -> `Environment resources (Docker
VM)`; `Postgres load` comes right after `Summary` because it is the first thing to check to know if
the database is saturated.

**New data sources this dashboard needs:**
- **postgres-exporter** (`deploy/local/compose.yaml`, `observability` profile): exposes on
  `postgres-exporter:9187/metrics` both the exporter's standard collections
  (`pg_stat_database_*`, `pg_stat_user_tables_*`, `pg_stat_bgwriter_*`, `pg_stat_activity_*`,
  `pg_database_size_bytes`, `pg_locks_count`, `pg_up`, ...) and the business ones from
  `deploy/local/postgres-exporter/queries.yaml` (`cobre_events_by_status`, `cobre_attempts_due`,
  `cobre_attempts_claimed_unfinished`, `cobre_attempts_executed_total`,
  `cobre_oldest_pending_age_seconds`). Job `postgres` in `prometheus.yml`.
- **node_exporter** (`deploy/local/compose.yaml`, `observability` profile): exposes on
  `node-exporter:9100/metrics` the `node_*` metrics for the entire Docker VM (CPU, load,
  memory, disk, network) — not per container. Job `node` in `prometheus.yml`. See "node_exporter"
  below: cAdvisor was tried first for per-container metrics and does not work under this
  OrbStack setup.
- **HTTP latency buckets**: `management.metrics.distribution.percentiles-histogram."http.server.requests"`
  in `application.yaml` (with `slo` at 50 ms/200 ms/500 ms/1 s). Without restarting api/worker with this
  change, `http_server_requests_seconds_bucket` does not exist yet, and the p95-by-uri panel is left
  without data (that is expected, not a query error).

### Summary (selected time range)

The summary counters use `$__range`, i.e. the time range selected in Grafana, and the `client_id` filter: narrowing the range to the last load-test run (or the last minute) reflects only that run, without carrying over earlier data. The two panels marked as a point-in-time snapshot (overdue backlog and events by status in Postgres) are gauges and do not depend on the range.

| Panel | Query | What it means |
|---|---|---|
| Completed deliveries (range) | `round(sum(increase(...{status="completed"}[$__range])))` | Completed transitions in the selected range. Rounded: `increase()` extrapolates between scrapes and yields fractions on sparse counters (a value such as 8.94 for nine events). |
| Failed deliveries (range) | `sum(increase(notifications_deliveries_total{status="failed"}[$__range]))` | Attempts that exhausted retries in the last hour. |
| Success rate (range) | `sum(increase(...{status="completed"}[$__range])) / (sum(increase(...{status="completed"}[$__range])) + sum(increase(...{status="failed"}[$__range])))` | Completed over final outcomes. The counter records state transitions, so `retrying` is excluded: an event that fails after five attempts counts once as failed, not five times. |
| Webhook latency p95 (range) | `histogram_quantile(0.95, sum by (le) (increase(notifications_webhook_latency_seconds_bucket[$__range])))` | p95 of the webhook POST, all clients. |
| Overdue backlog (worker) | `max(notifications_attempts_due)` | Overdue attempts not claimed, in-memory gauge on the worker (max across replicas). |
| Events by status (Postgres) | `cobre_events_by_status` | Current count of `notification_events` by `status`, from the database (not from the worker). |
| Duplicates (range) | `sum(increase(notifications_duplicates_total[$__range]))` | Redeliveries with an `event_id` already registered. |
| Skipped (range) | `sum(increase(notifications_skipped_total[$__range]))` | Received events the service decided not to register. |

### Postgres load

Everything that answers "how loaded is the database right now?", grouped in a single row
(job `postgres`, `datname="notifications"` unless stated otherwise).

| Panel | Query | What it means |
|---|---|---|
| Backends by state | `pg_stat_activity_count{datname="notifications"}` by `state` | Open sessions by state (`active`, `idle`, `idle in transaction`, ...). Many sustained `idle in transaction` sessions mean a client opening transactions and not closing them. |
| Transactions per second | `rate(pg_stat_database_xact_commit[5m])` / `rate(pg_stat_database_xact_rollback[5m])` | Moved from the `Database` row (not duplicated). |
| Tuples per second | `rate(pg_stat_database_tup_returned\|tup_fetched\|tup_inserted\|tup_updated\|tup_deleted[5m])` | Rows processed per second; the most direct signal of real workload on the database. |
| Blocks read: disk vs. cache per second | `rate(pg_stat_database_blks_read[5m])` / `rate(pg_stat_database_blks_hit[5m])` | How many 8 KB blocks are requested per second, split by whether they came from disk or from the buffer cache. |
| Cache hit ratio | `blks_hit / (blks_hit + blks_read)` | Moved from the `Database` row (not duplicated). |
| I/O time (read/write) | `rate(pg_stat_database_blk_read_time[5m])` / `rate(pg_stat_database_blk_write_time[5m])` | ms of I/O per wall-clock second. **No data in this stack:** `track_io_timing` is off (`pg_settings_track_io_timing = 0`); the panel states this in its description. |
| Average busy sessions (database load) | `rate(pg_stat_database_active_time_seconds_total[5m])` | Average number of sessions executing SQL (seconds of execution per second, summed across sessions). 1 = one session busy the whole time; above the VM's core count, saturation. |
| Longest running transaction | `pg_stat_activity_max_tx_duration{datname="notifications"}` | Seconds of the oldest open transaction; a long transaction holds locks and blocks autovacuum. |
| Temp files/bytes per second | `rate(pg_stat_database_temp_bytes[5m])` / `rate(pg_stat_database_temp_files[5m])` | How much sorting/hashing spills to disk because it does not fit in `work_mem`. |
| Checkpoints per second | `rate(pg_stat_bgwriter_checkpoints_timed_total[5m])` (by time) vs. `rate(pg_stat_bgwriter_checkpoints_req_total[5m])` (forced) | Many sustained "req" checkpoints indicate `max_wal_size` is too small for the write rate. |
| Buffers written: backend vs. checkpointer | `rate(pg_stat_bgwriter_buffers_backend_total[5m])` vs. `rate(pg_stat_bgwriter_buffers_checkpoint_total[5m])` | A backend writing its own dirty buffer (instead of the checkpointer) signals that the checkpointer cannot keep up. |
| Database size | `pg_database_size_bytes{datname="notifications"}` | Total on-disk size of the `notifications` database. |
| Scans per table: index vs. sequential | `rate(pg_stat_user_tables_idx_scan[5m])` vs. `rate(pg_stat_user_tables_seq_scan[5m])`, for `notification_events` and `delivery_attempts` | A high, sustained `seq_scan` on `delivery_attempts` indicates the partial index on overdue attempts is not being used. |

### Environment resources (Docker VM)

Via node_exporter (job `node`). **No data until the service is up** (`observability`
profile), but the queries were verified against a real `node_exporter` (see
"node_exporter" below). Unlike the discarded cAdvisor row, these panels look at the
whole VM, not at an individual container — except for the last two (JVM CPU and memory), which
are indeed per process because Micrometer reports them from inside each JVM.

| Panel | Query | What it means |
|---|---|---|
| Total CPU by mode (%) | `sum by (mode) (rate(node_cpu_seconds_total[5m])) / scalar(count(node_cpu_seconds_total{mode="idle"}))` | Fraction of the VM's total CPU capacity used by mode (the `scalar()` prevents the lack of labels on `count()` from blocking the match). Feeds `HostCpuSaturated`. Postgres load and per-container CPU are NOT here — see "node_exporter" below. |
| Load average vs. available cores | `node_load1/5/15` vs. `count(node_cpu_seconds_total{mode="idle"})` | If the sustained load exceeds the number of cores, there is more work ready to run than CPU. |
| Memory used vs. total (VM) | `node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes` vs. `node_memory_MemTotal_bytes` | Feeds `HostMemoryLow`. |
| Disk I/O: bytes read/written by device | `rate(node_disk_read_bytes_total[5m])` / `rate(node_disk_written_bytes_total[5m])` | By device (`vda`/`vdb` are the VM's real disks). |
| Disk I/O: io_time by device | `rate(node_disk_io_time_seconds_total[5m])` | Fraction of each second with at least one I/O operation in progress. |
| Network by interface | `rate(node_network_receive_bytes_total[5m])` / `rate(node_network_transmit_bytes_total[5m])` | By the VM's network interface. |
| Disk space (VM) | `node_filesystem_avail_bytes{mountpoint="/var/lib/docker"}` / `node_filesystem_size_bytes{...}` | The `/` mountpoint does not show up in node_exporter under this VM (its fstype falls into the default excluded-type filter); `/var/lib/docker` is used as a proxy, same physical disk. |
| JVM process CPU | `process_cpu_usage{job=~"notifications-api\|notifications-worker"}` | This one is per process (Micrometer, not node_exporter): CPU of api and worker separately. |
| Approximate JVM RSS memory | `sum by (job) (jvm_memory_used_bytes{job=~"notifications-api\|notifications-worker"})` | Approximation of RSS per process (heap + non-heap); does not include all native memory outside the JVM. |

## node_exporter

**What it is.** [`quay.io/prometheus/node-exporter`](https://github.com/prometheus/node_exporter)
(pinned at `v1.8.2`) reads `/proc` and `/sys` and exposes metrics for the whole VM — CPU by mode,
load average, memory, disk I/O by device, network by interface, filesystem space — on
`/metrics` (Prometheus format). It was added to the `observability` profile in `compose.yaml`, with no
published ports (only reachable within the `notifications` network); Prometheus scrapes it as job `node`
(`prometheus.yml`). It runs with `--pid host` and the three host volumes (`/proc`, `/sys`, `/`)
mounted `:ro`, so it can see the VM's real process and mount namespaces instead of the
container's own — this is the standard deployment recommended by the project, with no `privileged: true` and
without touching the Docker socket.

**Why not cAdvisor (or Telegraf `inputs.docker`).** Both were tried first, to get
per-container metrics instead of whole-VM ones, and neither works under this OrbStack setup: no
container can reach the Docker socket here (root or privileged, mounting the whole `/var/run`:
`permission denied`), which blocks any tool that needs to talk to the
daemon. cAdvisor was also tried via its alternative path that does not depend on the socket (it reads cgroups and
the storage driver directly), and it failed the same way because this daemon uses the containerd snapshotter
(`driver-type: io.containerd.snapshotter.v1`), which cAdvisor v0.52.1 cannot read to resolve the
read-write layer of a container (`failed to identify the read-write layer ID ...`); verified with a
real `tmp-cadvisor`, `no` `container_*` metric carried per-container data, only the root cgroup
(`id="/"`). `node_exporter` has neither of these two problems because it reads `/proc`/`/sys`
directly, without going through the Docker socket or storage driver.

**What this means for the dashboard.** The `Environment resources (Docker VM)` row reports the
VM as a whole, not container by container — except `JVM process CPU` and `Approximate JVM RSS
memory`, which are indeed per process because Micrometer reports them from inside each JVM, not
node_exporter. Postgres's *internal* load (queries, backends, transactions) is shown in the
`Postgres load` row via `postgres-exporter`, which also does not depend on the Docker socket. To see
**per-container** CPU/memory/network (including `postgres`), the alternative that does work on this
host is to run, in the terminal, outside any container:

```bash
docker stats --no-stream
```

## What is not instrumented

- **Depth of the `account-events` queue (ElasticMQ).** ElasticMQ does not expose its own
  Prometheus endpoint; its only HTTP observable is `GET /statistics/queues` (used by the
  container's healthcheck, not scraped). The dashboard uses the rate of
  `notifications_registered_total` (row "Ingestion") as a proxy: if it does not grow with the load reaching the
  API, that is a sign messages are piling up in the queue before reaching the worker, but
  it does not give an actual message count. A dedicated SQS/ElasticMQ exporter was not added to this
  stack (see "Decisions" in the commit); if the real number is needed, the evaluated alternative is
  a sidecar that periodically calls `GetQueueAttributes` (`ApproximateNumberOfMessages`,
  `ApproximateNumberOfMessagesNotVisible`) on ElasticMQ's SQS-compatible API and publishes it
  as a Micrometer gauge or via a `node_exporter` `textfile`.
- **`notifications_leases_expired_total`.** Defined in the code (`DeliveryMetrics.leaseExpired()`)
  but with no caller outside the unit test; the claim with `SKIP LOCKED` does not currently distinguish an
  expired lease from a new attempt. The `NotificationsLeaseExpirationsHigh` rule stays
  loaded (see "Alarms") but cannot fire until that emission exists.

## Alarms (`deploy/local/prometheus/alerts.yml`)

Prometheus rules (`curl -s localhost:9090/api/v1/rules`), the five from RFC section 16 plus
five from the service review and two more from this round (Postgres load and container
resources), eleven in total:

| Alarm | Condition | Action (runbook) |
|---|---|---|
| `NotificationsAttemptsDueBacklog` | `max(notifications_attempts_due) > 1500` for 5 min (~30 s of work for one worker at 50 attempts/tick) | Scale workers or check Postgres |
| `NotificationsClientFailureRateHigh` | Failed over final outcomes (`completed` + `failed`) per client > 20 % with at least 50 outcomes in 10 min | Warn the client, its endpoint is degraded |
| `NotificationsAttemptsDueMetricMissing` | `absent(notifications_attempts_due)` for 2 min | No worker is alive; restart |
| `NotificationsLeaseExpirationsHigh` | Expired leases > 10/min for 5 min | POSTs take longer than the lease; check timeouts |
| `NotificationsErrorLogRateHigh` | `rate(logback_events_total{level="error"}[5m]) > 0.5` for 5 min, by `job` | Check the logs of the affected job |
| `NotificationsApiServerErrors` | 5xx > 1% of requests to `notifications-api` for 5 min | Check the HTTP API panel and the API logs |
| `NotificationsDbPoolExhausted` | `hikaricp_connections_pending > 0` for 2 min | Check the Database panel and `pg_stat_activity`; consider raising `maximum-pool-size` |
| `PostgresDown` | `pg_up == 0` for 1 min | Check the `postgres` container |
| `NotificationsOldestPendingTooOld` | `cobre_oldest_pending_age_seconds > 120` for 5 min | Same as `NotificationsAttemptsDueBacklog`, but looking at Postgres instead of the in-memory gauge |
| `PostgresBusyBackendsAboveCores` | `rate(pg_stat_database_active_time_seconds_total{datname="notifications"}[5m]) > VM core count` for 5 min | The database is saturated; check scans by table, tuples per second, backends by state, and `delivery_attempts` indexes, or lower `batch-size` / worker replicas |
| `HostMemoryLow` | `node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes < 0.10` for 5 min | The Docker VM is running out of memory; raise the VM's memory limit (OrbStack/Docker Desktop) or reduce load |
| `HostCpuSaturated` | VM idle CPU `< 10%` for 5 min | The VM is CPU-saturated; reduce load or assign it more CPU |

`NotificationsAttemptsDueBacklog`, `NotificationsAttemptsDueMetricMissing`, and
`NotificationsClientFailureRateHigh` have real data today. `NotificationsLeaseExpirationsHigh` is loaded
but never fires because `notifications_leases_expired_total` is not emitted (see "What is not
instrumented"). `NotificationsDbPoolExhausted` and `PostgresDown` need `postgres-exporter`
up (`observability` profile); `NotificationsOldestPendingTooOld` also needs
`postgres-exporter/queries.yaml`; `NotificationsApiServerErrors` does not need the HTTP buckets from
point 1 because it uses `_count`, not `histogram_quantile`. `PostgresBusyBackendsAboveCores` has real data
today (same job `postgres` as the rest of the `Postgres load` row). `HostMemoryLow` and
`HostCpuSaturated` need `node-exporter` up (`observability` profile, job `node`); unlike
the discarded `ContainerMemoryNearLimit` (cAdvisor), these do have real data as soon as the
service is up, because node_exporter does not depend on the Docker socket or the storage
driver — see "node_exporter" above.

**Decision: `NotificationsDlqNotEmpty` was removed.** The original rule referenced
`notifications_dlq_messages_visible`, a gauge that never came to exist (ElasticMQ does not expose
Prometheus, and no service code publishes it). It was decided to remove it from the file instead of
leaving it loaded-but-inert: an alarm that can never fire is worse than not having one,
because in `GET /api/v1/rules` or in the team's alarm list it appears to give coverage it does not
provide. Restoring it first requires the metric to exist — see the dedicated exporter
alternative in "What is not instrumented" above, or a Micrometer gauge in the service that reads
`ApproximateNumberOfMessages` from the DLQ — and only then adding the rule back with that real source.

## Load test

`scripts/load_test.py` (standard Python 3, no dependencies) publishes a batch of events
directly to the SQS queue (ElasticMQ) and verifies end to end that none is lost and that
monitoring reflects what happened. It runs inside a `python:3.12-alpine` container on the
`account-event-notification` network, so it talks to the stack's internal hostnames
(`elasticmq:9324`, `http://notifications-api:8080`, `http://wiremock:8080`,
`http://prometheus:9090`), not the ports published on the host.

**What it does:**

1. Takes an initial snapshot of Prometheus (`notifications_registered_total`,
   `notifications_duplicates_total`, `notifications_deliveries_total` by status), clears WireMock's
   request journal, and registers a temporary priority-1 stub that returns 503
   for the events marked as failures for this run.
2. Publishes `--events` events (`LOAD-<run>-<n>` for the ones that should complete, `LOAD-<run>-F-<n>` the
   ones that should fail; `--fail-ratio` sets the proportion: a number, or `random`, the default, which draws a value between 0.1 % and 2 % per run, the order of magnitude a real fleet of receivers shows on a bad day; the chosen value and the number of induced failures are printed in the run header), spreading client (`CLIENT001..3`) and
   type (`credit_deposit`, `debit_purchase`, `credit_transfer`) round-robin, in batches of 10
   (`SendMessageBatch`) with `--concurrency` threads publishing in parallel.
3. Waits for the backlog to drain **without** querying each id per round: with 50,000 events, a
   `GET /notification_events/{id}` per non-terminal id every 2 s reached up to ~2,800
   requests/s against the API, competing for CPU with the service under test and with
   Grafana/Prometheus. Instead, every `POLL_INTERVAL_S` (5 s) it makes 6 cheap requests —
   `GET /notification_events?delivery_status=pending&limit=1` and `...=retrying&limit=1`, once
   per client — and considers the system drained when both lists come back empty for the three
   clients in two consecutive rounds (a single empty round is not enough: the background simulator
   emits ~1 event every 2 s that can appear as `pending` for just a few milliseconds). Each round
   prints the Prometheus backlog (`max(notifications_attempts_due)`) and the delivery delta
   by status since the run started (includes the simulator's background traffic).
4. **While the drain wait runs**, a second, independent generator keeps load
   against the self-service REST API (`--api-rps`, default 20; `--api-clients` threads, default
   4) — see the next point. It stops as soon as the wait ends (drained or by timeout) and
   never counts as part of the point-3 polling.
5. With the system already at rest (drained, or `--timeout` exhausted), it makes **a single pass** of
   `GET /notification_events/{id}` over all ids (`--poll-concurrency` threads, default 8)
   to classify each one's final state; if any id still lacks a terminal state after that
   pass, it retries only those ids up to 3 more times, 5 s apart, before reporting them
   as non-terminal. When done (drained or not), it deletes the failure stub (also if the
   run fails or is interrupted) and compares: events published vs. registered vs. lost (404
   on the final pass); expected vs. obtained completed/failed (the `-F-` ones must end
   `failed`, with cycle 0 at exactly 5 attempts and `attempts_count` a multiple of 5 — see
   "replays" below); **confirmed reception** (two variants, see the next section); the Prometheus
   deltas; the p95 of `notifications_webhook_latency_seconds`; and the max of
   `notifications_attempts_due` over the run's window.

**Two variants of the reception criterion.** WireMock only keeps the last
`--wiremock-journal-limit` requests in its journal (default 5000, same as
`--max-request-journal-entries` in `compose.yaml` — see "Limits" below, **do not raise it**: at
120,000 WireMock hangs because it scans the whole journal on every request). The
original criterion — sum of `attempts_count` from the API against the `POST /webhook` requests WireMock
received for this run (filtered by the `LOAD-<run>-` tag) — is only valid when all the run's
POSTs fit in that journal. Before evaluating, the script computes
`expected_posts = completed + 5×failed + 5×replays` (the replays from the REST phase, see below,
also cost 5 POSTs each) and decides:

- **Variant A** (`expected_posts <= --wiremock-journal-limit`): compares API attempts
  against WireMock's count, as before.
- **Variant B** (`expected_posts > --wiremock-journal-limit`): WireMock's count is not
  reliable (the journal has already rotated), so instead it reads `attempts[].response_status` from
  the final classification pass and requires (a) zero attempts with a null `response_status` — an attempt
  with a null `response_status` is an I/O error (timeout or connection) that never reached the
  receiver — and (b) that `-F-` ids have their attempts at 503. Both counts (numeric vs. null
  `response_status`) are always printed in the report, whether or not this variant is used for the PASS.

The report always states which variant applied and why (`expected_posts` computed vs. the
limit).

6. **Concurrent REST load** (point 4): while the drain runs, it spreads traffic across the
   three clients in turns as follows: 40% cursor-paginated listing (`GET
   /notification_events?limit=50`, following `next_cursor` up to 3 pages), 20% filtered listing
   (`delivery_status=failed` or `completed`, with a `from`/`to` window over the last hour), 25%
   detail of a random id from the run, 10% replay of one of the run's own `-F-` ids already in
   `failed` (if none is known yet, it falls back to a detail request; each replay
   adds a new cycle of up to 5 more attempts — hence the "5 attempts" criterion becoming
   "cycle 0 with 5 and `attempts_count` a multiple of 5", and `expected_posts` growing by 5 for each
   one), and 5% negative cases (no token, expects 401; detail of another client's id, expects 404). It
   measures per request type: count, p50/p95 latency as measured on the client, and status codes
   other than expected — printed in the `API REST under load` table. This phase exists because the
   drain polling barely touches the API (6 requests every 5 s); without it, the **HTTP API**
   row of the Grafana dashboard (rate and p95 by `uri`/`status`) and the per-route percentiles have no
   real traffic to show during a run.

**How to run it** (with the stack already up, `make up` or `make up-all`):

```bash
make load                                          # 2000 events, 10% failure, 20 req/s of API
make load EVENTS=200 FAIL_RATIO=0.20 TIMEOUT=120    # explicit parameters (FAIL_RATIO=random by default)
make load CONCURRENCY=16                            # more publishing threads
make load API_RPS=0                                 # no REST load phase
make load API_RPS=50 API_CLIENTS=8                  # more load on the REST API
make load WIREMOCK_JOURNAL_LIMIT=5000               # force the journal limit (default)
```

`--poll-concurrency` (default 8) controls the threads of the final classification pass (one per
id, with the system already drained); it does not affect the round-based polling, which always makes 6 fixed requests
regardless of `--events`. `--api-rps 0` disables the REST load phase entirely.

The target generates the three demo tokens with `scripts/token.sh` on the host and passes them to
the container as environment variables (`TOKEN_CLIENT001`, `TOKEN_CLIENT002`, `TOKEN_CLIENT003`); if
`scripts/load_test.py` is invoked by hand outside the target, they must be exported first.

**What `RESULT: PASS` means.** All criteria must hold at once: zero lost events;
`completed` and `failed` obtained equal to expected (the exact `-F-` ids, cycle 0 with 5
attempts and `attempts_count` a multiple of 5); confirmed reception (variant A or B, as
applicable — see above); the `notifications_duplicates_total` delta at zero; and, if `--api-rps`
> 0, zero 5xx responses and zero unexpected codes in the REST load. Anything else
(including failing to reach a terminal state before the timeout during the final classification) is
`RESULT: FAIL` with exit code 1. Failing to reach drain within `--timeout` alone is
only a WARN if the final classification still finds all ids in a terminal state (this can
happen with the simulator's background traffic competing with the polling). The Prometheus deltas
and the latency/backlog metrics are always printed, whether `PASS` or `FAIL` (they are
informational and do not gate the result, because the event simulator keeps emitting in parallel and
moves them).

**Tool limits:**

- WireMock's request journal keeps at most **5000** entries by default
  (`--max-request-journal-entries 5000` in `compose.yaml`) — **do not raise this limit**: at
  120,000 entries WireMock hangs under load because it scans the whole journal on every
  incoming request. With the default values (2000 events, 10% failure) the run
  generates at most ~2,800 of its own POSTs and fits comfortably; beyond that (or with `EVENTS` much
  larger, or many replays from the REST phase) the script simply switches to variant B of the reception
  criterion (see above) instead of comparing against a WireMock count that has already rotated.
- By default there is only one `notifications-worker` replica, with `batch-size: 50` per 1 s
  cycle: the delivery ceiling is around 50 events/s. To raise it, scale before launching the
  load test: `docker compose -f deploy/local/compose.yaml --env-file .env --profile infra --profile app up -d
  --scale notifications-worker=3` (do not run `make down`/`up` while the load test is running).
- Resetting WireMock's journal uses `DELETE /__admin/requests` (the real endpoint for WireMock
  3.13.1 in this image; `POST /__admin/requests/reset` does not exist in this image and returns
  404).
- The REST load phase is not synchronized with event publishing: if it starts requesting
  details for the run's ids before the consumer has processed them, it can see transient 404s
  in the `detail` bucket (this is explicitly tolerated, and does not count as an unexpected code).

**What to look at in Grafana during the run.** With `make up-all` running, open
`http://localhost:3001` and watch, as the load runs: **Delivery rate by status** should
show the spike of `completed` followed by the trickle of `failed` about ~30 s later (retry
backoff); **Attempts due** rises while the batch is pending and returns to 0 when it finishes — if it
stays high, the worker cannot keep up (see "Limits" above, scale replicas); **Webhook latency p95
by client** should not move much unless artificial latency is added; **Failures by client
(last hour)** should show only the run's `LOAD-<run>-F-*` events (plus anything that had already
failed before); **HTTP API** (rate and p95 by `uri`/`status`, 4xx/5xx, active requests) now
has real traffic to show while the drain runs thanks to the REST load phase from point
6 — before this change that row was nearly empty, because the drain polling only makes 6
cheap requests every 5 s.

On a large run (tens of thousands of events, several minutes), avoid leaving the dashboard on
a long range like "Last 6 hours" with a short auto-refresh: on an already loaded VM that adds
Grafana's own queries to CPU contention and can get them canceled by timeout.
Use a range sized to the run (e.g. "Last 15 minutes" or "Last 30 minutes") and an
auto-refresh of 10 s or more; if it still looks slow, close the dashboard while the load test runs and
reopen it when done with the run's exact interval fixed.

## Demo with an external receiver

Delivery trial against a real, public HTTPS receiver (not WireMock), to test the full
path: signature, headers, TLS, and how `WebhookUrlValidator` behaves against a public host.

**1. Create an ephemeral receiver on webhook.site:**

```bash
curl -s -X POST https://webhook.site/token
# {"uuid":"<uuid>", ...}
```

The receiver URL is `https://webhook.site/<uuid>`; received requests are listed at
`https://webhook.site/token/<uuid>/requests?sorting=newest`.

**2. Point the seed subscriptions at the receiver.** The URL of the three subscriptions (`CLIENT001`,
`CLIENT002`, `CLIENT003`) is set when the database is created, in
`V2__initial_subscriptions.sql` (placeholder `${webhookUrl}`, resolved from `WEBHOOK_URL` by
`spring.flyway.placeholders.webhookUrl`, see `application-api.yaml`). Changing `WEBHOOK_URL` in
`.env` only affects new databases, so the volume must be recreated:

```bash
# In .env (do NOT commit):
#   WEBHOOK_URL=https://webhook.site/<uuid>
#   WEBHOOK_ALLOWLIST=        (empty: the host is public and HTTPS, no allowlist needed)
make down     # deletes the Postgres volume
make up       # reruns Flyway with the new URL
```

**3. Check the received requests** (wait ~30 s for the simulator to emit the reference batch):

```bash
curl -s "https://webhook.site/token/<uuid>/requests?sorting=newest"
```

Every request carries the body `{"id","event_key","client_id","created_at","content"}` and the
headers `event-timestamp`, `event-signature`, `x-cobre-event-id`, `x-cobre-attempt`.

**4. Verify the signature with `openssl`** (HMAC-SHA256 of `timestamp + "." + body`, the client's
subscription key — `local-signing-key-client001`, `...client002`, `...client003`, see
`V2__initial_subscriptions.sql`):

```bash
TS="2026-09-16T02:15:06.399958866Z"
BODY='{"id":"EVT004","event_key":"debit_automatic_payment","client_id":"CLIENT002","created_at":"2024-03-15T12:05:33Z","content":"Monthly utility bill payment of $85.50"}'
printf '%s.%s' "$TS" "$BODY" | openssl dgst -sha256 -hmac "local-signing-key-client002"
# => b962e23bb239c8644e19365626851a979728ace220ccd1534a844bbbc3a950d1
# matches byte for byte the event-signature header for that request.
```

**5. Confirm in the API** that the reference events end up `completed`:

```bash
make token CLIENT=CLIENT001
curl -s localhost:8080/notification_events -H "Authorization: Bearer <token>"
```

**Actual result of this trial (2026-09-15):** webhook.site received and logged the requests (50
kept in its history, the free plan's maximum); body and all four headers
correct in 100% of those inspected, and the HMAC-SHA256 signature verified with `openssl`
matched byte for byte (example `EVT004`/`CLIENT002` above). Of the ten reference events,
4 (`EVT003`, `EVT004`, `EVT005`, `EVT006`) reached `completed` on the first attempt. The other
six stayed in `retrying`/`pending`: under the simulator's sustained load
(`SIMULATOR_EMIT_INTERVAL=2s` x 3 clients, plus retries) webhook.site started returning
`429 Too Many Requests` — visible in each event's `attempts[].response_status` — and the block
persisted for more than 7 minutes even after stopping the simulator and probing with a
manual request (`curl -o /dev/null -w '%{http_code}' -X POST https://webhook.site/<uuid>` kept returning
`429`). The retry and backoff pipeline (`RetryPolicy`, `application-local.yaml`:
`base-delay=2s`, `factor=4`, `max-delay=10s`, `max-attempts=5`) behaved exactly as
expected against that transient failure: each event moved to `retrying` and retried with exponential
backoff until exhausting its 5 attempts. Conclusion: the delivery path (signature, headers, TLS,
public URL validation) is proven end to end; the limit came from the free receiver's
abuse policy, not from the system. For a sustained trial without that limit, use a
receiver you control (Postman Echo, a local server exposed with `ngrok`, or similar) or stop the
simulator (`docker compose ... stop event-simulator`) as soon as the reference batch has been emitted.

**6. Switch back to WireMock:**

```bash
# In .env: restore the values from .env.example
#   WEBHOOK_URL=http://wiremock:8080/webhook
#   WEBHOOK_ALLOWLIST=wiremock
make down
make up   # or make up-all
```
