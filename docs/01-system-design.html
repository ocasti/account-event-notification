Cobre Notifications

Webhook notification delivery service and self-service API so each client can query and resend its own events. Hexagonal architecture in Java 21 and Spring Boot 4.1.

Version 2Status: acceptedLocal run in Docker ComposeCloud target: AWS

Summary

Problem. The Cobre platform generates financial events, and its clients need to receive them by webhook with reliable retries, and to query and resend them on their own. Cobre's current webhook is best-effort and offers neither query nor resend.

Solution. A service with a hexagonal architecture in Java 21 and Spring Boot, deployed as two processes from the same image: a JWT-protected self-service API and a worker that consumes events from an SQS queue, resolves the client's subscription, delivers over HTTPS with an HMAC signature, retries with backoff, and persists every attempt in PostgreSQL. The API exposes three endpoints: filtered listing, detail, and replay of failed deliveries. Locally everything runs in Docker Compose with a simulated issuer that generates events from the reference dataset; in AWS the same pieces map to SQS, Fargate and RDS with no code changes.

Guarantees. Every event is registered exactly once; every attempt is executed by a single worker; delivery to the client is at least once and the client deduplicates it by identifier. A client only sees and resends its own events.

1. Who calls whom

The confusion about the external URL is resolved by looking at the direction of each arrow. There are two channels, and they run in opposite directions.

Practical consequence: the receiver's URL is injected as WEBHOOK_URL in each client's seed subscription. Nothing needs to be exposed to the internet for the local demo. The Cobre platform is business context: in this scope it does not exist as a system that talks to us. The simulated issuer takes its place and honors the contract; in production it is replaced by the real bus and the consumer does not change.

Contract of the event that travels through the queue

The reference dataset mixes event data with the outcome of its delivery. delivery_date and delivery_status are outputs of our system, not inputs, so the issuer's contract does not carry them.

A single data path. Every event that exists in the system entered through the queue and went through the full flow. The simulated issuer uses the reference dataset as a template: on startup it publishes its ten events with their original identifiers and date, and afterward keeps generating derived events, with new identifiers and combinations of client, type and content taken from the file, at a configurable rate. It also accepts one-off events via POST /simulator/events. Each event's delivery state is computed by the system; the delivery_status and delivery_date fields from the file are not part of the contract: they are the expected outcome, and in the local environment WireMock responds 503 to exactly EVT003, EVT005 and EVT009 so the system reproduces that outcome through its own behavior.

2. System context

C4 context level. Three actors around a single system. The Cobre platform produces events; the client receives and queries them; the monitoring team observes.

3. Containers

C4 container level. One codebase, one image, two processes with different reasons to exist: the API exists to answer HTTP requests from clients; the worker exists to drain the queue and the attempts table. They start with different Spring profiles. If the API goes down, deliveries keep going out; if the worker goes down, messages wait in the queue and nothing is lost.

4. The hexagon

Three Maven modules. domain is a flat, pure-Java package; application splits into application.port (output ports) and application.usecase (the five use cases); infrastructure groups the adapters under infrastructure.{config,persistence,rest,security,webhook,worker}. Neither of the first two depends on Spring or on any infrastructure library, and ArchUnit verifies this in CI. Arrows always point inward.

Rules ArchUnit enforces

Six rules in HexagonalArchitectureTest, under infrastructure/src/test/java/co/cobre/notifications/architecture/:

  • domain imports nothing from application or infrastructure, nor the org.springframework, jakarta, com.fasterxml or tools.jackson (Jackson 3) packages.
  • application imports no infrastructure and none of those same framework packages. The core's only interfaces are the output ports, in the application.port package; use cases are concrete classes in application.usecase, with no inbound interface, and adapters invoke them directly.
  • Every class annotated @Entity resides in infrastructure.persistence.
  • infrastructure.rest does not depend on infrastructure.persistence: controllers only call use cases, never repositories or JPA entities.
  • infrastructure.worker does not depend on infrastructure.rest or infrastructure.security, and infrastructure.rest does not depend on infrastructure.worker: the api and worker processes stay isolated at compile time, not only by Spring profile.

Test code has its own rules. A TestConventionsTest in every module (domain, application, infrastructure and the simulator) fails the build if a test calls a lax Mockito matcher (any(), isA(), argThat()), depends on reflection, or has a name outside the should<Result>When<Condition> pattern. Test data comes from object mothers and builders in co.cobre.notifications.domain.fixtures, packaged as the domain test jar and consumed by the other modules, with a fixed clock and identifiers from the reference dataset.

Build gates. mvnw verify runs PMD on production and test code (unused imports and private members, empty or generic catch blocks, lost stack traces, an if nested inside another, cyclomatic or cognitive complexity above 8, NPath above 50, confusing ternaries) and JaCoCo with a 100 % line-coverage minimum per module; both run in CI. The production code has no else branches and no nested control statements: guard clauses and early returns, one nesting level per method, exhaustive switch expressions over sealed types.

5. Lifecycle of a notification

The reference dataset only carries completed and failed. For "definitely failed" to mean something, the domain needs intermediate states. Invalid transitions throw a domain exception and the controller translates it to 409.

Retry policy

AttemptWait before the attemptWith ±20% jitterState if it fails
10 s (immediate)—RETRYING
230 s24 – 36 sRETRYING
32 min96 – 144 sRETRYING
48 min6.4 – 9.6 minRETRYING
515 min (cap)12 – 15 minFAILED

The policy is configurable, under notifications.retry.* in application.yaml: base-delay, factor, max-delay, jitter-ratio and max-attempts are properties of RetryProperties, read by RetryConfig to build the domain's RetryPolicy. The defaults are the ones in the table: base 30 seconds, factor 4, cap 15 minutes, jitter ±20%, 5 attempts; about 26 minutes total until FAILED. The 15-minute cap is not arbitrary, it is the maximum for SQS's DelaySeconds, so the same policy works unchanged if retries move to the queue in the future. The local profile (application-local.yaml) overrides base-delay to 2 s and max-delay to 10 s (RETRY_BASE_DELAY and RETRY_MAX_DELAY variables), which fits the five attempts into under a minute with no code changes. A replay opens a new cycle: the event's cycle column is incremented, the attempt counter resets to zero within that cycle, and the event has its five attempts again. 4xx errors other than 408 and 429 are not retried: the client's endpoint is saying the request is invalid, and repeating it changes nothing.

6. Sequence: delivery with retries

From the event the platform emits to the final state. This is the flow that covers the five required capabilities: subscription verification, HTTPS delivery, retries, persisting the result, and observability.

7. Sequence: client-isolated query

client_id never travels as a parameter. It comes from the token, and every repository receives that value as a mandatory filter. This is the direct mitigation for Broken Object Level Authorization, the first item in the OWASP API Top 10.

8. Sequence: replay of a failed delivery

Replay sends nothing synchronously. It enqueues a new attempt and returns 202; the same worker from section 6 delivers it. This way the API does not depend on the client webhook's latency, and replay inherits retries, signing and metrics with no extra code.

9. Data model

Three tables. created_at is the date of the business fact, the issuer's occurred_at, and it is the one the API filters on; received_at is the reception time and is used to measure latency. Attempts are stored one per row, grouped by cycle, so a client complaint can be answered with the exact history. The primary key is event_id: the platform is assumed to guarantee globally unique identifiers, as Cobre does with its prefixed identifiers.

What monitoring observes in near real-time

  • gauge due attempts pending: if it grows, the worker cannot keep up or the client is down.
  • counter notifications.deliveries{client_id, status, event_key}: failure rate per client, basis for alarms.

  • log one JSON line per attempt with event_id, client_id, attempt_number, response_status and correlation_id. This answers any complaint with evidence.

11. Patterns applied, and why this is not a Saga

The Cobre platform is event-driven and microservices-based. These are the patterns this design genuinely applies, with the exact place where they live, and the one it deliberately does not apply.

PatternWhere it lives in the designWhat it guarantees
Claim-based job table (outbox-style)delivery_attempts table; the worker drains it. Not a classic outbox because it does not publish to a broker: the "consumer" is the worker itselfRegistering the event and scheduling its first attempt happen in a single local transaction. Every PENDING event is born with its attempt; SKIPPED has no attempts by definition.
At-least-once delivery + idempotent consumerRetries and replay on our side; event_id on every POST for the client's sideWe can resend without fear. The webhook contract requires the client to tolerate duplicates by event_id.
Retry with backoff and dead letterRetryPolicy in the domain; FAILED state as the queue of failures; replay as manual redriveA down client does not aggressively consume resources, and a definitive failure stays visible and recoverable.
Competing consumersWorker replicas over the same queue and batch claim with conditional writes on the tableHorizontal scaling with no duplicate deliveries.
Event notification (Fowler)Minimal webhook payload; the self-service API for detailThe client learns that something happened and queries if it needs more. Less coupling to the internal schema.
Tenant isolationclient_id derived from the JWT and mandatory on every repository queryA client cannot see or resend another client's events.

Why this is not a Saga

A Saga coordinates a business transaction that spans several services, each with its own local transaction, and defines compensations to undo earlier steps when a later one fails. The canonical example: create order, charge, reserve inventory; if inventory fails, refund.

  • There is no distributed business transaction to keep consistent. The payment already happened before the event reaches us. Notifying is a side effect the payment's outcome does not depend on.
  • There is no compensation. If the webhook definitively fails, nothing upstream is undone. Retrying and marking FAILED is not compensating. Neither is replay: it re-executes the same step, it does not revert another.
  • Where a Saga does live: in the platform that issues the events. A payment that debits one account, credits another, and posts to the ledger is almost certainly coordinated with a Saga. Our service would be an observer at the end of that chain, never a participant with compensation.
  • What would turn this into a Saga: if registering a subscription required verifying the URL with a challenge and registering the endpoint with a third party, with rollback of the registration when the third party fails. That would involve compensation. It is not in scope.

Startup

  • Chain: postgres and elasticmq → notifications-api (migrates) → notifications-worker → event-simulator. All with depends_on and condition: service_healthy.
  • Healthchecks: pg_isready for Postgres; /actuator/health/readiness for api and worker; for WireMock, GET /__admin/health. For ElasticMQ, the image is pinned at softwaremill/elasticmq-native:1.6.12: it exposes /statistics/queues on port 9325 via busybox's wget, which is what the healthcheck uses; the 1.7.x series removed that statistics server in both the native and JVM images, so it is not upgraded without first deciding on a different probe.
  • One network, no volume for Postgres. docker compose down leaves the environment clean; Flyway rebuilds the schema and the simulator starts emitting again.
  • Configuration: .env.example versioned, .env ignored. To point at a different receiver, only WEBHOOK_URL is edited. Ports parameterized in .env with a preflight script that checks for free ports and available Docker memory before starting.
  • Development cycle: infrastructure in containers, the application on the host with ./mvnw spring-boot:run. Rebuilding the image for every change is a loop of minutes; on the host it is seconds. Integration tests use Testcontainers and do not depend on Compose.

Terraform: no

No Terraform is written. Alternatives considered: an infra/terraform folder written but never applied, validated in CI; or a Terraform container in Compose. Discarded because infrastructure code that is never applied is visible debt with nothing backing it, and because Terraform is not a runtime service. The infrastructure-as-code within actual scope is Compose, and the AWS design in section 10 names the modules that would be needed: queue with DLQ, two Fargate services, RDS and SSM parameters. If added in the future, it will only be with terraform validate in CI, never applied.

13. Concurrency: four workers and one message

With several worker replicas, there are three points where the same event could be processed twice. Each has its own barrier, and no single barrier covers all three. The resulting guarantee is at least once toward the client, exactly once in our state.

Where it can duplicateBarrierWorst case
Four workers poll the queue and a message arrivesSQS / ElasticMQ visibility timeout. The worker that receives it hides it from the others; it is deleted only when the listener finishes without an exception (ON_SUCCESS mode). Timeout configured longer than the registration time.The worker crashes after registering and before acknowledging. The message reappears and another worker receives it. Moves to barrier 2.
Two workers register the same event_idPrimary key. Event and attempt #1 are inserted in a single transaction. The second insert fails on uniqueness; the code treats it as "already registered," acknowledges the message and creates no attempt.None. Postgres serializes the race even if it happens in the same millisecond. This also covers the producer emitting the same event_id twice.
Four workers poll delivery_attempts and there are due rowsSKIP LOCKED + lease + conditional write. TX1: SELECT … FOR UPDATE OF d SKIP LOCKED LIMIT batch-size brings up to batch-size due, free rows (or with an expired lease) without another worker being able to read those same rows while the transaction stays open; an in-memory filter applies max-per-client; and an UPDATE … WHERE id IN (:ids) marks claimed_at and claimed_by using Postgres's clock for the ids its own UPDATE managed to mark, then commits. The POSTs run outside the transaction and in parallel, one per virtual thread. TX2 records the result only if the row is still claimed by claimed_by equal to this instance and not yet executed. The lease lasts twice the maximum time of a POST, so an entire batch fits within it.A worker crashes between the POST and recordResultIf: the row stays claimed until the lease expires, and another worker picks it up and retries the send. The only case of duplication toward the client; the claim step itself no longer allows two workers to take the same row. The webhook contract requires idempotency by event_id, same as Stripe or GitHub.
Two simultaneous replays on the same FAILED eventState-conditional update: UPDATE … WHERE event_id = ? AND status = 'FAILED'. Both read FAILED; the second UPDATE affects zero rows and returns 409.None. Only one attempt is created.
API and worker update the same event at the same timeEvery state transition is an UPDATE conditional on the source state.Whoever loses sees zero rows affected and does not overwrite the other's state.

Why the POST does not run inside the lock's transaction

It would be simpler to keep the FOR UPDATE open during the HTTP call: if the worker dies, the transaction rolls back on its own and the row is freed. But a slow webhook holds a database connection for up to five seconds per attempt, and with four workers and batches of fifty rows the pool runs out under load. The lease costs two columns and one condition in the WHERE clause, and is the direct answer to what happens to the pool under load.

Why not a FIFO queue

SQS FIFO offers deduplication by MessageDeduplicationId for five minutes and ordering by group. Not needed: events are independent, order does not matter, and the primary key deduplicates with no time window. FIFO limits throughput and adds configuration without removing any of the three barriers.

How it is demonstrated

  • Integration test (persistence/DeliveryAttemptRepositoryAdapterIT, testClaimDueConcurrency): twenty due attempts and four real workers calling claimDue concurrently (with no external transaction), verifying that the union of what was claimed covers all twenty. That each result is written only once is proved separately by the recordResultIf tests in the same class.
  • Listener test (worker/AccountEventListenerIT, listenDuplicateEventOnlyRegistersOnce): the same message delivered twice to the queue reaches the listener twice, which delegates to RegisterNotificationEvent the decision not to register the event twice.
  • In the local environment: docker compose up -d --scale notifications-worker=4, emit twenty events, and count exactly twenty POSTs to /webhook in WireMock (/__admin/requests/count).

Decision: Postgres. The API's requirement is exactly what a relational index solves without designing keys upfront, and the attempt claim is demonstrated with a readable integration test. DynamoDB is cheaper at E1 and scales further at E3, but it forces a redesign of the claim step and anticipating every filter in a GSI. MongoDB adds no differential advantage over either one here. The answer would only change with sustained E3 or active-active multi-region, and in that case the right move is not DynamoDB as the primary store but SQS with delay as the retry scheduler and the database only as the record, which works the same for Postgres and for DynamoDB, and which the hexagon allows because it is a new adapter behind the same port.

Decisions derived from the capacity analysis

  • Scheduler every 1 second, with no special path for the first attempt. Event→delivery p50 latency of about 500 ms with a single delivery mechanism. The alternative of running attempt #1 inline inside the listener was discarded: it requires its own executor, a lease that starts before the POST, and an edge the hexagon does not have.
  • Batch claim equal to the worker's HTTP parallelism (batch-size 50, virtual threads) with SELECT … FOR UPDATE OF d SKIP LOCKED followed by an UPDATE … WHERE id IN (:ids) per batch (DeliveryAttemptRepositoryAdapter.claimDue), and a per-client row cap (max-per-client) within the batch so a client with thousands of retries cannot monopolize the workers. Larger batches and an adaptive interval remain an evolution for E3.
  • Backoff capped at 15 minutes, the maximum for SQS's DelaySeconds, so the policy works unchanged if retries migrate to the queue. Already reflected in section 5.
  • Partial index on the outbox (next_attempt_at) WHERE executed_at IS NULL: it contains only pending rows and does not grow with the table. The due-attempts metric is computed over that index, never with COUNT(*) over the full table.
  • Keyset pagination in the API, never offset-based.
  • Documented evolutions, out of the current scope: circuit breaker per subscription for down clients; in-memory subscription cache; honoring Retry-After on 429; bulk replay by date range and state.
  • Production evolutions, with their precondition: monthly partitioning by created_at from E2 onward, which requires changing the primary key to (event_id, created_at) and the attempts foreign key to a composite one, with archiving to S3 before dropping partitions for financial retention; fillfactor=70 on attempts, which only benefits the claim step because writing the result touches an indexed column; PgBouncer from E2 onward; a read replica for the API from E3 onward.

Signals to change storage, and what happens first

Signals: sustained commit p99 above 20 ms with batching already applied; autovacuum not keeping up with the attempts table, with more than 20% dead tuples; or a real active-active multi-region requirement. Before changing engines, in order: batching, fillfactor, partitioning, subscription cache, splitting the hot table from history, read replica, retries to SQS with delay. Only after that, and only by pattern, DynamoDB for hot state with Postgres for querying and history.

Local load test

Ten minutes on the laptop, with no pretense of simulating AWS: four workers, WireMock with a fixed 300 ms delay and 10% 503s, a burst of 5,000 events from the simulator, and 60 seconds of oha with 50 connections against the API's GET. Delivered per second, p50 and p99 event→delivery, Postgres transactions per second, API p99 and Docker CPU are measured. Expected result: four workers with 50 POSTs in flight each and 300 ms per POST give about 600 deliveries per second, capped by WireMock, API p99 under 50 ms and Postgres under 20% CPU. Conclusion: locally and untuned, the database absorbs hundreds of events per second; the design supports a hundred thousand events per hour with a medium instance, and a million per hour with partitioning, a replica and batching. The limit is set by the client's webhook, not Postgres. The repository is a port: if volume changes the access pattern, the change is an adapter, not a redesign.

15. Contrast with Cobre's public API

Cobre already offers a publicly documented notifications and subscriptions API in production. This design adopts its names, its event schema and its signing algorithm, so that a current client would not have to change its integration. And the contrast shows precisely what this design adds.

16. Closed decisions

Detail decisions that complete the design: subscription model, signature, replay idempotency, token issuance, webhook contract, observability and security.

Subscription

A subscription is a URL plus a list of event keys, same as in Cobre. In the current scope one event produces exactly one notification: event_id is the primary key and the notification references the client's single active subscription that includes the event's key. If a client had two matching subscriptions, the system takes the oldest one and logs it; delivering to several would require an intermediate notification-per-subscription table and remains a declared evolution. Initial subscriptions are loaded by data migration, one per client with a wildcard and the configured receiver URL; with no CRUD in scope, this is the only way to create them. With no active subscription for the key, the event is saved as SKIPPED, which is not replayable in this scope: it returns 409 with the reason. With more clients: index (client_id, active), and subscription CRUD as an evolution with the four endpoints Cobre already exposes.

Webhook signature

Implemented, with Cobre's algorithm and headers. event-signature = HMAC-SHA256(event_signature_key, event-timestamp + "." + body). The key is stored in the database and never returned in full by the API; encryption at rest and rotation with two active keys are evolutions. A 5-minute tolerance window on the timestamp, documented for the receiver. This is what lets the client verify that the POST comes from Cobre and was not altered.

Replay idempotency

State rule plus optimistic locking only. Two replays on the same event: the second receives 409. The Idempotency-Key header is withdrawn from scope and noted as an evolution. Sequence 8 and the data model updated accordingly.

JWT tokens in the local environment

RS256 with a key pair generated locally, same as Cobre's real token. make token CLIENT=CLIENT002 uses the private key to sign a JWT with sub equal to the client, a fixed audience and a 20-minute expiration, the same lifetime Cobre documents. SecurityConfig configures the resource server: it validates the signature with NimbusJwtDecoder.withPublicKey(...) loaded from a file (JwtProperties.publicKey, a Resource of type file:) and adds an audience JwtClaimValidator on top of JwtValidators.createDefault(). The name of the claim that identifies the client and the expected audience are configuration (JwtProperties.clientClaim, JwtProperties.audience; variables JWT_CLIENT_CLAIM, JWT_AUDIENCE), read by ClientIdResolver. Controllers do not read the JWT directly: AuthenticatedClientArgumentResolver resolves any parameter annotated @AuthenticatedClient by taking the Jwt from the JwtAuthenticationToken in the security context and delegating to ClientIdResolver. Exact equivalence with the real token is verified at integration time. The POST /auth endpoint is not implemented because it already exists on the platform; in local, the command replaces it.

Two Grafana dashboards, provisioned from deploy/local/grafana: Notifications (deliveries by state, p95 per client, due attempts, failures per client) and Notifications · Service review, with rows for summary, deliveries, ingestion, errors, API HTTP, JVM and database. Our own metrics are emitted by the MeteredNotificationEventRepository and MeteredWebhookSender decorators over the ports ProcessDueDeliveries consumes; the database ones come from postgres_exporter with business queries (events by state, due attempts, claimed but not finished, age of the oldest due attempt); the HTTP ones carry histograms for per-route percentiles; environment load (CPU, memory, disk and network of the Docker VM) comes from node_exporter, and each JVM process reports its own CPU and memory metrics. ElasticMQ's queue depth is not instrumented: the registration rate is used as an approximation. Per-container CPU is not collected from within the stack because under OrbStack the Docker socket is not reachable from the containers; on the host, docker stats provides it. Alarms designed, each with its action (all wired up except the one for expired leases, which depends on notifications.leases.expired, defined in DeliveryMetrics.leaseExpired() and still without an emission point): due attempts above 30 seconds of worker work for 5 minutes → scale workers or check Postgres; a client's failure rate above 20% with at least 50 deliveries in 10 minutes → notify the client, its endpoint is degraded; due-attempts metric absent for 2 minutes → no worker is alive, restart; log error rate above 0.5 per second for 5 minutes → check the process log; API 5xx above 1% for 5 minutes → check the API; connection pool with waiting requests for 2 minutes → grow the pool or check slow queries; Postgres down for 1 minute → restore the database; oldest due attempt older than 2 minutes for 5 minutes → the worker is not draining, scale; expired leases above 10 per minute → POSTs are taking longer than the lease, check timeouts, pending notifications.leases.expired being wired up. DLQ: a message moves to the dead-letter queue after 5 receives without an ack; it is never redriven automatically. DLQ depth has no alarm because ElasticMQ exposes no metrics for it; in AWS, CloudWatch provides it (ApproximateNumberOfMessagesVisible). Logs: one line per attempt (webhook delivery attempt, emitted by MeteredWebhookSender) with event_id, client_id, cycle, attempt_number, outcome, response_status, latency_ms and reason on failures; never the body or the signature. The json profile enables Spring Boot's ECS output (logging.structured.format.console: ecs). A correlation_id propagated from the SQS message remains an evolution. Internal team access: as the owner of the information, it answers a client complaint by querying the attempts table, the per-client dashboards and the logs directly; the self-service API is exclusively for clients and does not expose one client's data to another, not even to internal roles.

18. Assumptions, non-goals and open risks

Assumptions

  • The issuing platform guarantees a globally unique event_id. A repeated event_id with different content is ignored, logged and counted in a metric.
  • The reference dataset is an event template, not an initial state: its outcome fields are the expected result in local, not pre-loaded data.
  • The production JWT token is issued by the Cobre platform; the client claim and audience are configured at integration time.
  • A client has one active subscription per event key. Delivering to several subscriptions of the same client is out of scope.
  • The client's receiver is idempotent by id and tolerates out-of-order delivery, as Cobre's contract requires.

Non-goals

  • Subscription CRUD, signing-key rotation, replay of completed or SKIPPED events, bulk replay by range.
  • Circuit breaker per subscription, application-level rate limiting, subscription cache, encryption at rest for the signing key.
  • Deployment to AWS, Terraform, Kubernetes, multi-region, distributed tracing.
  • Retries via SQS with delay, partitioning, PgBouncer, read replica: evolutions with preconditions described in section 14.

Open risks

  • Version compatibility. Spring Boot 4.1 with Spring Cloud AWS 4.1 is verified in the first phase; fallback: Spring Boot 4.0.
  • ElasticMQ version. Pinned to 1.6.12 because 1.7.x removed the statistics server the healthcheck relies on; upgrading requires first deciding on a different probe.
  • Duplicate POST after a crash between sending and writing the result. Inherent to at-least-once delivery; measured with notifications.leases.expired.
  • Deployment with two versions coexisting. Flyway migrates from the API; schema changes follow the expand-then-contract rule, and the queue contract stays compatible with the previous worker version.
  • Retention and regulation. Event content may include financial data; final retention and archiving before deletion are defined with the compliance area.

20. Glossary

LeaseTimestamp with which a worker declares that it owns an attempt for a given period; once the period expires, another worker can take it.
CycleSet of up to five delivery attempts. The original registration opens cycle 0; each replay opens a new one.
DLQDead-letter queue: where SQS deposits a message that could not be acknowledged after several receives.
KeysetCursor-based pagination over ordered columns, instead of numeric offset; its cost does not grow with the page.
Port and adapterIn hexagonal architecture, the port is the interface the core defines; the adapter is the technical implementation that fulfills it.
SKIP LOCKEDPostgreSQL clause that makes a query skip rows locked by another transaction instead of waiting.
SSRFServer-side request forgery: getting the server to make requests to internal destinations the attacker cannot reach directly.
Visibility timeoutTime during which SQS hides a received message from other consumers until it is acknowledged or expires.
