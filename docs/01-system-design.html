Cobre Notifications

Servicio de entrega de notificaciones por webhook y API self-service para que cada cliente consulte y reenvíe sus propios eventos. Arquitectura hexagonal en Java 21 y Spring Boot 4.1.

Versión 2Estado: aceptadoEjecución local en Docker ComposeObjetivo cloud: AWS

Resumen

Problema. La plataforma de Cobre genera eventos financieros y sus clientes necesitan recibirlos por webhook con reintentos confiables, y consultarlos y reenviarlos por sí mismos. El webhook actual de Cobre es best-effort y no ofrece consulta ni reenvío.

Solución. Un servicio con arquitectura hexagonal en Java 21 y Spring Boot, desplegado como dos procesos de una misma imagen: una API self-service protegida con JWT y un worker que consume eventos de una cola SQS, resuelve la suscripción del cliente, entrega por HTTPS con firma HMAC, reintenta con backoff y persiste cada intento en PostgreSQL. La API expone tres endpoints: listar con filtros, detalle y replay de entregas fallidas. En local todo corre en Docker Compose con un emisor simulado que genera eventos a partir del conjunto de datos de referencia; en AWS las mismas piezas se mapean a SQS, Fargate y RDS sin cambiar el código.

Garantías. Cada evento se registra exactamente una vez; cada intento lo ejecuta un solo worker; la entrega al cliente es al menos una vez y el cliente la deduplica por identificador. Un cliente solo ve y reenvía sus propios eventos.

1. Quién llama a quién

La duda de la URL externa se resuelve mirando la dirección de cada flecha. Hay dos canales y van en sentidos opuestos.

Consecuencia práctica: la URL del receptor se inyecta como WEBHOOK_URL en la suscripción semilla de cada cliente. No hay que exponer nada a internet para la demostración local. La plataforma de Cobre es contexto de negocio: en este alcance no existe como sistema que nos hable. El emisor simulado ocupa su lugar y respeta el contrato; en producción se reemplaza por el bus real y el consumidor no cambia.

Contrato del evento que viaja por la cola

El conjunto de datos de referencia mezcla datos del evento con el resultado de su entrega. delivery_date y delivery_status son salidas de nuestro sistema, no entradas, así que el contrato del emisor no las lleva.

CampoTipoOrigenEjemplo
event_idstring, únicoemisorEVT003
event_typestringemisorcredit_transfer
client_idstringemisorCLIENT002
contentstringemisorBank transfer received from Account #4567 for $1,500.00

Un solo camino de datos. Todo evento que existe en el sistema entró por la cola y pasó por el flujo completo. El emisor simulado usa el conjunto de datos de referencia como plantilla: al arrancar publica sus diez eventos con sus identificadores originales y su fecha, y después sigue generando eventos derivados, con identificadores nuevos y combinaciones de cliente, tipo y contenido tomadas del archivo, a un ritmo configurable. También acepta eventos puntuales por POST /simulator/events. El estado de entrega de cada evento lo calcula el sistema; los campos delivery_status y delivery_date del archivo no forman parte del contrato: son el resultado esperado, y en el entorno local WireMock responde 503 exactamente a EVT003, EVT005 y EVT009 para que el sistema reproduzca ese resultado por su propio comportamiento.

2. Contexto del sistema

Nivel de contexto C4. Tres actores alrededor de un único sistema. La plataforma de Cobre produce eventos; el cliente los recibe y consulta; el equipo de monitoreo observa.

3. Contenedores

Nivel de contenedores C4. Un solo código, una sola imagen, dos procesos con razones de vivir distintas: la API existe para responder HTTP a los clientes; el worker existe para drenar la cola y la tabla de intentos. Se arrancan con perfiles de Spring diferentes. Si la API cae, las entregas siguen saliendo; si el worker cae, los mensajes esperan en la cola y nada se pierde.

4. El hexágono

Tres módulos Maven. domain y application no dependen de Spring ni de ninguna librería de infraestructura, y ArchUnit lo verifica en CI. Las flechas siempre apuntan hacia adentro.

Reglas que ArchUnit hace cumplir

  • domain no importa nada de application ni de infrastructure, ni paquetes org.springframework, jakarta.persistence o com.fasterxml.
  • application solo importa domain. Los puertos son interfaces del paquete application.port.in y application.port.out.
  • Los controllers solo llaman puertos de entrada; nunca repositorios ni entidades JPA.
  • Las entidades JPA viven en infrastructure.persistence y se traducen al dominio con mappers explícitos. El dominio no lleva anotaciones.

5. Ciclo de vida de una notificación

El conjunto de datos de referencia solo trae completed y failed. Para que "definitely failed" signifique algo, el dominio necesita estados intermedios. Las transiciones inválidas lanzan excepción de dominio y el controller las traduce a 409.

Política de reintentos

IntentoEspera antes del intentoCon jitter ±20 %Estado si falla
10 s (inmediato)—RETRYING
230 s24 – 36 sRETRYING
32 min96 – 144 sRETRYING
48 min6.4 – 9.6 minRETRYING
515 min (tope)12 – 15 minFAILED

Base 30 segundos, factor 4, tope 15 minutos: unos 26 minutos en total hasta FAILED. El tope de 15 minutos no es casual, es el máximo de DelaySeconds de SQS, así la misma política sirve si en el futuro los reintentos se mueven a la cola. Un replay abre un ciclo nuevo: el contador vuelve a cero y el evento dispone otra vez de los cinco intentos. Para demostraciones los tiempos se acortan por configuración (por ejemplo base 2 s) para ver los cinco intentos en menos de un minuto. Los errores 4xx distintos de 408 y 429 no se reintentan: el endpoint del cliente está diciendo que la petición es inválida, y repetirla no cambia nada.

6. Secuencia: entrega con reintentos

Del evento que emite la plataforma hasta el estado final. Es el flujo que cubre las cinco capacidades requeridas: verificación contra suscripción, entrega HTTPS, reintentos, persistencia del resultado y observabilidad.

7. Secuencia: consulta aislada por cliente

El client_id nunca viaja como parámetro. Sale del token, y todos los repositorios reciben ese valor como filtro obligatorio. Es la mitigación directa a Broken Object Level Authorization, la primera del OWASP API Top 10.

8. Secuencia: replay de una entrega fallida

El replay no envía nada de forma síncrona. Encola un intento nuevo y responde 202; el mismo worker de la sección 6 lo entrega. Así la API no depende de la latencia del webhook del cliente y el replay hereda reintentos, firma y métricas sin código adicional.

9. Modelo de datos

Tres tablas. created_at es la fecha del hecho de negocio, occurred_at del emisor, y es la que filtra la API; received_at es la hora de recepción y sirve para medir latencia. Los intentos se guardan uno por fila, agrupados por ciclo, para que una queja de cliente se responda con el historial exacto. La clave primaria es event_id: se asume que la plataforma garantiza identificadores globalmente únicos, como hace Cobre con sus identificadores prefijados.

Qué observa monitoreo en near real-time

  • gauge intentos pendientes vencidos: si crece, el worker no da abasto o el cliente está caído.
  • counter notifications.deliveries{client_id, status, event_key}: tasa de fallo por cliente, base de las alarmas.
  • histogram latencia del POST al webhook por cliente: detecta degradación del endpoint del cliente antes de que él se queje.
  • log una línea JSON por intento con event_id, client_id, attempt_number, response_status y correlation_id. Con eso se responde cualquier reclamo con evidencia.

11. Patrones aplicados y por qué no es Saga

La plataforma de Cobre es event driven y de microservicios. Estos son los patrones que este diseño aplica de verdad, con el lugar exacto donde viven, y el que deliberadamente no aplica.

PatrónDónde vive en el diseñoQué garantiza
Tabla de trabajos con reclamo (estilo outbox)Tabla delivery_attempts; el worker la drena. No es un outbox clásico porque no publica a un broker: el "consumidor" es el propio workerRegistrar el evento y programar su primer intento ocurren en una sola transacción local. Todo evento PENDING nace con su intento; SKIPPED no tiene intentos por definición.
Entrega al menos una vez + consumidor idempotenteReintentos y replay de nuestro lado; event_id en cada POST para el lado del clientePodemos reenviar sin miedo. El contrato del webhook exige al cliente tolerar duplicados por event_id.

Por qué no es un Saga

Un Saga coordina una transacción de negocio que cruza varios servicios, cada uno con su transacción local, y define compensaciones para deshacer los pasos anteriores cuando uno posterior falla. El ejemplo canónico: crear orden, cobrar, reservar inventario; si el inventario falla, reembolsar.

  • No hay transacción de negocio distribuida que mantener consistente. El pago ya ocurrió antes de que el evento llegue a nosotros. Notificar es un efecto secundario del que no depende el resultado del pago.
  • No hay compensación. Si el webhook falla definitivamente no se deshace nada aguas arriba. Reintentar y marcar FAILED no es compensar. Replay tampoco: es volver a ejecutar el mismo paso, no revertir otro.
  • Dónde sí vive un Saga: en la plataforma que emite los eventos. Un pago que debita una cuenta, acredita otra y asienta en el ledger casi seguro se coordina con un Saga. Nuestro servicio sería un observador al final de esa cadena, nunca un participante con compensación.
  • Qué lo convertiría en Saga: si dar de alta una suscripción exigiera verificar la URL con un challenge y registrar el endpoint en un tercero, con reversión del alta cuando el tercero falla. Ahí habría compensación. No está en alcance.

Decisiones de empaquetado, contenedores, arranque y orden de construcción. Cada una indica la alternativa considerada y la razón de la elección.

Imágenes: dos, no tres ni una

El perfil apaga beans, no solo configura. Listener SQS y scheduler llevan @Profile("worker"); controllers y seguridad web llevan @Profile("api"). En perfil api el proceso no abre conexión a la cola. Flyway migra solo en la API; el worker espera a que la API esté healthy, y así escalar workers nunca produce carrera de migraciones.

Construcción: Dockerfile multi-stage con mvnw, sin Buildpacks ni Jib. Etapa de build sobre eclipse-temurin:21-jdk: copia los POM y cachea dependencias en una capa, luego copia el código y empaqueta. Etapa final sobre eclipse-temurin:21-jre, usuario no root, jar extraído en capas para que las dependencias no se reconstruyan al cambiar una línea de Java. Reproducible con docker compose build en cualquier máquina con Docker, sin Java ni Maven instalados. Buildpacks descarga cientos de MB la primera vez y Jib es un plugin más que explicar.

Grafana se incorpora en la última fase como dashboard provisionado por archivo. Alternativa considerada: incluirlo desde la fase de entrega para mostrar "near real-time" desde el inicio. Se descarta porque un dashboard con paneles vacíos o a medias comunica lo contrario de lo que pretende. Las métricas con nombre definitivo se definen en la fase de entrega en Micrometer; Grafana es entonces solo un archivo JSON con tres paneles. Mientras tanto, /actuator/prometheus ya cubre el requisito de observabilidad. Ningún contenedor dedicado a infraestructura: no hay nada que aprovisionar que Compose no levante ya. Flyway crea el esquema dentro de la API y ElasticMQ se configura con un archivo montado que declara la cola y su DLQ.

Arranque

  • Cadena: postgres y elasticmq → notifications-api (migra) → notifications-worker → event-simulator. Todo con depends_on y condition: service_healthy.
  • Healthchecks: pg_isready para Postgres; /actuator/health/readiness para api y worker. Para ElasticMQ, verificar en la primera fase si la imagen nativa trae wget; si no, usar la imagen JVM softwaremill/elasticmq o dejar que el listener reintente la conexión al arrancar.
  • Una red, sin volumen para Postgres. docker compose down deja el entorno limpio; Flyway rehace el esquema y el simulador vuelve a emitir.
  • Configuración: .env.example versionado, .env ignorado. Para apuntar a un receptor distinto solo se edita WEBHOOK_URL. Puertos parametrizados en .env con un script preflight que verifica puertos libres y memoria disponible en Docker antes de arrancar.
  • Ciclo de desarrollo: infraestructura en contenedores, aplicación en el host con ./mvnw spring-boot:run. Reconstruir imagen por cada cambio es un loop de minutos; en el host es de segundos. Los tests de integración usan Testcontainers y no dependen de Compose.

Terraform: no

No se escribe Terraform. Alternativas consideradas: una carpeta infra/terraform escrita pero nunca aplicada, validada en CI; o un contenedor de Terraform en Compose. Se descartan porque código de infraestructura nunca aplicado es deuda visible sin nada que lo respalde, y porque Terraform no es un servicio de runtime. La infraestructura como código del alcance real es Compose, y el diseño AWS de la sección 10 nombra los módulos que harían falta: cola con DLQ, dos servicios Fargate, RDS y parámetros en SSM. Si se agrega en el futuro, será solo con terraform validate en CI, sin aplicarlo.

13. Concurrencia: cuatro workers y un mensaje

Con varias réplicas del worker hay tres puntos donde un mismo evento podría procesarse dos veces. Cada uno tiene su barrera, y ninguna barrera sola cubre los tres. La garantía resultante es al menos una vez hacia el cliente, exactamente una vez en nuestro estado.

Dónde puede duplicarseBarreraQué pasa en el peor caso
Cuatro workers hacen polling de la cola y llega un mensajeVisibility timeout de SQS / ElasticMQ. El worker que lo recibe lo oculta a los demás; se borra solo cuando el listener termina sin excepción (modo ON_SUCCESS). Timeout configurado mayor al tiempo de registro.El worker se cae después de registrar y antes de confirmar. El mensaje reaparece y otro worker lo recibe. Pasa a la barrera 2.
Dos workers registran el mismo event_idClave primaria. Evento e intento #1 se insertan en una sola transacción. La segunda inserción falla por unicidad; el código la trata como "ya registrado", confirma el mensaje y no crea intento.Ninguno. Postgres serializa la carrera aunque ocurra en el mismo milisegundo. También cubre que el productor emita dos veces el mismo event_id.
Cuatro workers hacen polling de delivery_attempts y hay filas vencidasFOR UPDATE SKIP LOCKED + arrendamiento por lote + escritura condicional. TX1 corta: toma tantas filas vencidas y libres como POST puede ejecutar en paralelo, marca claimed_at y claimed_by con el reloj de Postgres, confirma. Los POST corren fuera de transacción y en paralelo. TX2 graba el resultado solo si la fila sigue reclamada por esta instancia. El arrendamiento dura el doble del tiempo máximo de un POST, así que un lote entero cabe dentro de él.El worker se cae entre el POST y TX2. El arrendamiento vence y otro worker repite el POST. Duplicado hacia el cliente, inevitable sin transacción distribuida. El contrato del webhook exige idempotencia por event_id, igual que Stripe o GitHub.
Dos replays simultáneos sobre el mismo evento FAILEDActualización condicional al estado: UPDATE … WHERE event_id = ? AND status = 'FAILED'. Ambos leen FAILED; el segundo UPDATE afecta cero filas y responde 409.Ninguno. Solo se crea un intento.
API y worker actualizan el mismo evento a la vezToda transición de estado es un UPDATE condicional al estado de origen.Quien pierde ve cero filas afectadas y no pisa el estado del otro.

Por qué el POST no va dentro de la transacción del lock

Sería más simple mantener el FOR UPDATE abierto durante el HTTP: si el worker muere, la transacción se revierte sola y la fila queda libre. Pero un webhook lento retiene una conexión de base de datos hasta cinco segundos por intento, y con cuatro workers y lotes de cincuenta filas el pool se agota bajo carga. El arrendamiento cuesta dos columnas y una condición en el WHERE, y es la respuesta directa a la pregunta de qué pasa con el pool bajo carga.

Por qué no cola FIFO

SQS FIFO ofrece deduplicación por MessageDeduplicationId durante cinco minutos y orden por grupo. No hace falta: los eventos son independientes, el orden no importa y la clave primaria deduplica sin ventana de tiempo. FIFO limita el throughput y añade configuración sin quitar ninguna de las tres barreras.

Cómo se demuestra

  • Test de integración con Testcontainers: veinte intentos vencidos, cuatro pollers concurrentes sobre la misma tabla, y la aserción de que cada intento fue reclamado exactamente una vez y ejecutado exactamente una vez.
  • Test de registro duplicado: el mismo mensaje entregado dos veces al listener produce un solo evento y un solo intento.
  • En el entorno local: docker compose up -d --scale notifications-worker=4, emitir veinte eventos, y mostrar en el registro de peticiones de WireMock exactamente veinte POST.

Decisión: Postgres. El requisito de la API es exactamente lo que un índice relacional resuelve sin diseñar claves por adelantado, y el reclamo de intentos se demuestra con un test de integración legible. DynamoDB es más barato en E1 y escala más en E3, pero obliga a rediseñar el reclamo y a anticipar cada filtro en un GSI. MongoDB no aporta ventaja diferencial frente a ninguno de los dos aquí. La respuesta cambiaría solo con E3 sostenido o multi-región activa-activa, y en ese caso el movimiento correcto no es DynamoDB como base principal sino SQS con delay como programador de reintentos y la base solo como registro, que sirve igual para Postgres y para DynamoDB, y que el hexágono permite porque es un adaptador nuevo detrás del mismo puerto.

Decisiones derivadas del análisis de capacidad

  • Scheduler cada 1 segundo, sin camino especial para el primer intento. Latencia evento→entrega p50 de unos 500 ms con un solo mecanismo de entrega. La alternativa de ejecutar el intento #1 en línea dentro del listener se descartó: exige un executor propio, un arrendamiento que empieza antes del POST y una arista que el hexágono no tiene.
  • Reclamo por lote igual al paralelismo HTTP del worker (50, virtual threads) con UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED LIMIT 50) RETURNING, repetido dentro del mismo tick mientras el lote vuelva lleno, y tope de filas por cliente dentro del lote para que un cliente con miles de reintentos no monopolice a los workers. Lotes mayores e intervalo adaptativo quedan como evolución para E3.
  • Tope del backoff en 15 minutos, el máximo de DelaySeconds de SQS, para que la política sirva sin cambios si los reintentos migran a la cola. Ya reflejado en la sección 5.
  • Índice parcial del outbox (next_attempt_at) WHERE executed_at IS NULL: contiene solo las filas pendientes y no crece con la tabla. La métrica de intentos vencidos se calcula sobre ese índice, nunca con COUNT(*) sobre la tabla completa.
  • Paginación por keyset en la API, nunca por offset.
  • Evoluciones documentadas, fuera del alcance actual: circuit breaker por suscripción para clientes caídos; caché en memoria de suscripciones; honrar Retry-After en 429; replay masivo por rango de fechas y estado.
  • Evoluciones de producción, con su precondición: particionado mensual por created_at desde E2, que exige cambiar la clave primaria a (event_id, created_at) y la clave foránea de intentos a compuesta, con archivo a S3 antes de borrar particiones por retención financiera; fillfactor=70 en intentos, que solo beneficia al reclamo porque la escritura del resultado toca una columna indexada; PgBouncer desde E2; réplica de lectura para la API desde E3.

Señales para cambiar el almacenamiento, y qué se hace antes

Señales: commit p99 sostenido por encima de 20 ms con lotes ya aplicados; autovacuum que no alcanza a la tabla de intentos, con más de 20 % de tuplas muertas; o requisito real de multi-región activa-activa. Antes de cambiar de motor, en orden: lotes, fillfactor, particionado, caché de suscripciones, separar tabla caliente de histórico, réplica de lectura, reintentos a SQS con delay. Solo después, y solo por patrón, DynamoDB para el estado caliente con Postgres para consulta e histórico.

Test de carga local

Diez minutos en la laptop, sin pretender simular AWS: cuatro workers, WireMock con 300 ms de retardo fijo y 10 % de 503, una ráfaga de 5 000 eventos desde el simulador, y 60 segundos de oha con 50 conexiones sobre el GET de la API. Se miden entregas por segundo, p50 y p99 evento→entrega, transacciones por segundo de Postgres, p99 de la API y CPU de Docker. Resultado esperable: cuatro workers con 50 POST en vuelo cada uno y 300 ms por POST dan unas 600 entregas por segundo, limitadas por WireMock, API p99 por debajo de 50 ms y Postgres por debajo del 20 % de CPU. Conclusión: en local y sin afinar, la base absorbe cientos de eventos por segundo; el diseño soporta cien mil eventos por hora con una instancia mediana, y un millón por hora con particionado, réplica y lotes. El límite lo pone el webhook del cliente, no Postgres. El repositorio es un puerto: si el volumen cambia el patrón de acceso, el cambio es un adaptador, no un rediseño.

16. Decisiones cerradas

Decisiones de detalle que completan el diseño: modelo de suscripción, firma, idempotencia del replay, emisión de tokens, contrato del webhook, observabilidad y seguridad.

Suscripción

Una suscripción es una URL más una lista de claves de evento, igual que en Cobre. En el alcance actual un evento produce exactamente una notificación: event_id es la clave primaria y la notificación referencia la única suscripción activa del cliente que incluya la clave del evento. Si un cliente tuviera dos suscripciones que coincidan, el sistema toma la más antigua y lo registra en log; entregar a varias exigiría una tabla intermedia notificación-por-suscripción y queda como evolución declarada. Las suscripciones iniciales se cargan por migración de datos, una por cliente con comodín y la URL del receptor configurada; sin CRUD en el alcance, es la única forma de crearlas. Sin suscripción activa para la clave, el evento se guarda como SKIPPED, que no es replayable en este alcance: responde 409 con la razón. Con más clientes: índice (client_id, active), y el CRUD de suscripciones como evolución con los cuatro endpoints que Cobre ya expone.

Firma del webhook

Se implementa, con el algoritmo y los headers de Cobre. event-signature = HMAC-SHA256(event_signature_key, event-timestamp + "." + cuerpo). La clave se guarda en la base y nunca se devuelve completa por la API; el cifrado en reposo y la rotación con dos claves activas son evoluciones. Ventana de tolerancia de 5 minutos sobre el timestamp, documentada para el receptor. Es lo que permite al cliente verificar que el POST proviene de Cobre y no fue alterado.

Idempotencia del replay

Solo regla de estado más bloqueo optimista. Dos replays sobre el mismo evento: el segundo recibe 409. La cabecera Idempotency-Key se retira del alcance y se menciona como evolución. Secuencia 8 y modelo de datos actualizados.

Tokens JWT en el entorno local

RS256 con un par de claves generado en local, igual que el token real de Cobre. make token CLIENT=CLIENT002 firma con la clave privada un JWT con sub igual al cliente, audiencia fija y expiración de 20 minutos, la misma vida que documenta Cobre. La API valida solo con la clave pública, que es lo que haría en producción contra el JWKS del emisor de Cobre. El origen de la clave, el claim de cliente y la audiencia son configuración; la equivalencia exacta con el token real se verifica cuando se integre. El endpoint POST /auth no se implementa porque ya existe en la plataforma; en local lo sustituye el comando.

18. Supuestos, no-objetivos y riesgos abiertos

Supuestos

  • La plataforma emisora garantiza event_id globalmente único. Un event_id repetido con contenido distinto se ignora, se registra en log y se cuenta en métrica.
  • El conjunto de datos de referencia es una plantilla de eventos, no un estado inicial: sus campos de resultado son el desenlace esperado en local, no datos pre-cargados.
  • El token JWT de producción lo emite la plataforma de Cobre; el claim de cliente y la audiencia se configuran al integrar.
  • Un cliente tiene una suscripción activa por clave de evento. Entregar a varias suscripciones del mismo cliente queda fuera del alcance.
  • El receptor del cliente es idempotente por id y tolera entregas fuera de orden, como exige el contrato de Cobre.

No-objetivos

  • CRUD de suscripciones, rotación de claves de firma, replay de eventos completados o SKIPPED, replay masivo por rango.
  • Circuit breaker por suscripción, rate limiting en la aplicación, caché de suscripciones, cifrado en reposo de la clave de firma.
  • Despliegue en AWS, Terraform, Kubernetes, multi-región, trazas distribuidas.
  • Reintentos vía SQS con delay, particionado, PgBouncer, réplica de lectura: evoluciones con precondiciones descritas en la sección 14.

Riesgos abiertos

  • Compatibilidad de versiones. Spring Boot 4.1 con Spring Cloud AWS 4.1 se verifica en la primera fase; alternativa: Spring Boot 4.0.
  • Healthcheck de ElasticMQ. Si la imagen nativa no trae cliente HTTP, se usa la imagen JVM o el listener reintenta la conexión.
  • POST duplicado tras caída entre el envío y la escritura del resultado. Inherente a la entrega al menos una vez; se mide con notifications.leases.expired.
  • Despliegue con dos versiones conviviendo. Flyway migra desde la API; los cambios de esquema siguen la regla de expandir primero y contraer después, y el contrato de la cola se mantiene compatible con la versión anterior del worker.
  • Retención y regulación. El contenido de los eventos puede incluir datos financieros; la retención definitiva y el archivo previo al borrado se definen con el área de cumplimiento.

20. Glosario

ArrendamientoMarca temporal con la que un worker declara que un intento es suyo durante un plazo; vencido el plazo, otro worker puede tomarlo.
CicloConjunto de hasta cinco intentos de entrega. El registro original abre el ciclo 0; cada replay abre uno nuevo.
DLQCola de mensajes fallidos: donde SQS deposita un mensaje que no pudo confirmarse tras varias recepciones.
KeysetPaginación por cursor sobre las columnas ordenadas, en lugar de por desplazamiento numérico; su costo no crece con la página.
